# RAG Eval: retrieval evaluation for Thai documents

RAG Eval measures how well a RAG pipeline finds the right passage in
Thai documents, so you can choose the chunking method, chunk size, retriever and
embedding model from numbers instead of guesses.

Two separate evaluations on the same documents and QA sets:

- **ประเมิน Embedding (retrieval):** where does the chunk that really answers each question
  rank? Rank p50 / p95, Hit@1/3/5/10, MRR, nDCG@10. Compare chunking, embedding models
  (local Hugging Face models, or Voyage / OpenAI / Ollama over an API) and BM25 / dense /
  hybrid retrieval. No LLM, fast and free
- **ประเมิน RAG (end to end):** one retrieval config, the top k chunks go to an LLM that
  answers, and a judge LLM (which can differ from the answering one) grades each answer
  against the reference. % correct, % grounded in the documents, and for every wrong
  answer whether retrieval missed the chunk or the LLM answered badly
- **Any LLM:** Claude, or any OpenAI-compatible server (Ollama, LM Studio, vLLM, OpenAI).
  Set the base URL, API key and model on the **ตั้งค่า LLM** page
- **Questions from any file:** drop an Excel, CSV, PDF, Word or text file (20 MB max,
  `MAX_UPLOAD_MB`). Tables with question/answer columns (Thai or English headers, detected
  automatically) become questions directly; other tables and documents go to the LLM,
  which writes the questions into a new QA set
- **Several QA sets:** keep separate sets (e.g. samples, real user questions, hard cases), copy
  one to start a variant, and pick which set a benchmark runs on. Each run records its set
- **QA set:** written by hand, imported from Excel / CSV / JSON, or generated by the LLM from
  your documents. Export to Excel (with filters and a `use` column), screen the questions,
  and import back: rows are matched by `id`, `use = no` drops a row
- **Compare runs:** tick several runs and see every config in one table, with deltas against a baseline
- **Chunk map:** a React Flow view of document → chunk → question, showing which chunk holds each answer
- **ลองถาม (playground):** ask one question with one config and see the ranked chunks, scores, timing and the LLM answer
- **วิธีการวัด:** a step-by-step page on the method, with the formulas and references
- **API:** Swagger UI at `/api/docs` (ReDoc at `/api/redoc`). Long tasks (import, upload,
  generation, benchmark) return a job; poll `GET /api/jobs/{id}` for progress
- **Thai-aware chunking:** `char` (baseline that cuts mid-word), `word` (snaps to Thai
  word boundaries with PyThaiNLP), `recursive` (paragraph → line → phrase → word). The
  document page shows where each method cuts and how many chunks were split mid-word.

## How the ground truth works

Each question stores its **evidence**: the exact text in the document that supports the
answer, saved as a character span (document, start, end). Each chunk also keeps its own
span. A retrieved chunk counts as a hit when it covers at least half of the smaller of
the two spans. Because of this, **one QA set works with every chunking config**, and
you don't need to relabel anything when you change the chunk size.

| Metric | Meaning |
| --- | --- |
| Hit@k | share of questions whose evidence is in the top k chunks (also called Hit Rate or Recall@k) |
| MRR | mean of 1 / rank of the first hit (0 if not found within k max) |
| nDCG@10 | binary-relevance nDCG over the top 10, the headline score of BEIR and MTEB |
| Coverage@k | share of evidence characters contained in the union of the top k chunks |
| Latency p50 / p90 / p95 / p99 | time from query to ranked results, per question: query embedding + search (warm-up excluded) |
| ตอบถูก / อิงเอกสาร | answer correctness (correct = 1, partial = 0.5) and share of answers fully grounded in the context, both graded by the LLM |

## Run with Docker

```bash
docker compose up --build    # http://localhost:8000, embeddings on CPU
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up --build   # NVIDIA GPU (CUDA 12.8)
```

Two services: `frontend` (nginx serving the built React app on port 8000, proxying
`/api`) and `backend` (FastAPI). `./data` is mounted into the backend, so documents, QA
sets, runs and settings stay on your disk. Downloaded embedding models live in the
`hf-models` volume.

The LLM is not part of the compose file. Run Ollama or LM Studio however you like, then
enter it on the **ตั้งค่า LLM** page. Inside Docker the presets already point at
`http://host.docker.internal:<port>/v1`, which reaches servers on your machine.

## Run without Docker

Requires Python 3.10+ and Node 20+.

```bash
# backend
cd backend
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
# NVIDIA GPU (optional, much faster embeddings): install the CUDA build of torch first
#   pip install torch --index-url https://download.pytorch.org/whl/cu128
pip install -r requirements.txt
uvicorn app.main:app --port 8000

# frontend, in another terminal
cd frontend
npm install
npm run dev                        # http://localhost:5173, proxies /api to :8000
```

Or run `npm run build` once; the backend then serves `frontend/dist` itself at
http://localhost:8000.

Open the app and click **โหลดชุดตัวอย่าง** to load 3 fictional Thai documents and 29
questions, then go to Benchmark.

### LLM settings

Open **ตั้งค่า LLM**:

1. Pick a provider: Claude, Ollama, LM Studio, OpenAI, or any OpenAI-compatible server.
2. Fill in the base URL, API key (not needed for Ollama or LM Studio) and model. Leave the
   model empty and press **ทดสอบการเชื่อมต่อ** to fetch the server's model list.
3. The test sends one short prompt. If it passes, the settings are saved and the page
   links to the next step. If it fails, nothing is saved and the error is shown.

Settings are saved in `data/settings.json`, which is git-ignored. Environment variables
in a `.env` file at the project root work as defaults (see `.env.example`).
If Ollama runs on Windows and the backend runs in WSL, and `localhost` doesn't connect,
use the Windows host IP or set `networkingMode=mirrored` in `.wslconfig`.

Using the same model both to answer and to grade tends to inflate scores, and small
local models grade Thai less reliably, so read through a sample of the verdicts.

Retrieval evaluation does not need an LLM at all.

## Importing a QA set

CSV or JSON with these columns:

| column | required | |
| --- | --- | --- |
| question | yes | |
| answer | recommended | used by the generation grader |
| evidence | yes | copy the text exactly from the document; whitespace differences are tolerated |
| document | no | file name; if omitted, all documents are searched |

See `samples/qa.json` for an example. Rows whose evidence can't be found in any
document are reported and skipped.

## Tips for a meaningful test

- Write questions the way users ask them, not by copying sentences from the document.
  The sample set does this, which is why dense retrieval beats BM25 on it.
- 29 questions is a demo. For decisions, use 100+ questions from your real documents.
  Generate them with Claude, then read and fix them.
- Thai PDFs often extract badly (vowels and tone marks out of order). Check the
  extracted text on the document page. If it's broken, convert the file to text with
  a better tool first.
- Latency depends on the machine. Compare configs within one run, not across machines.

## Layout

```
backend/app/
  chunking.py   Thai-aware chunkers with exact offsets
  retrieval.py  dense (sentence-transformers), BM25 (PyThaiNLP tokens), hybrid (RRF)
  metrics.py    span-overlap hits, Hit@k, MRR, coverage, percentiles
  llm.py        Claude or OpenAI-compatible: QA generation, answering, judging
  runner.py     background benchmark and generation jobs
  main.py       FastAPI routes
frontend/src/   Vite + React + TypeScript
  pages/        Documents, QA, Bench, Runs, RunDetail, Questions, Settings
  components/   Layout, HitCurve, LatencyList, Ruler (the rank ruler), ui
samples/        fictional Thai documents + QA set
data/           your documents, QA sets (data/qa/), runs and settings (JSON, created on first run)
```
